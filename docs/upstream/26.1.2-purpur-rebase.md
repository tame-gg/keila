# Keila -> Purpur 26.1.2 Re-base Runbook

Status: **phase 1 landed (base + toolchain) / phase 2 blocked on build env.**
Chosen path: re-base Keila onto **Purpur 26.1.2**, dropping the Leaf dependency.

- **Phase 1 (done, this branch):** `gradle.properties` set to the 26.1.2 base
  (`mcVersion`/`apiVersion=26.1.2`, `paperCommit=76d2ac7…`), decouple scaffolding
  removed, and the toolchain moved to **Java 25** (root + leaf-server build files,
  both CI workflows, `.java-version`, README). This does **not** build yet — the
  patch set below still targets 1.21.11 — and CI will be red until phase 2.
- **Phase 2 (pending capable env):** single-file `build.gradle.kts` patch rebase
  against Paper `main`, `mache -> 26.1.2+build.3`, the `--enable-preview` audit,
  vendoring Purpur's base patches, the ~400-patch re-port, and the Leaf->Purpur
  identity reframe. Needs PaperMC/Mojang network + Java 25. Decision made
with the trade-off understood: Purpur contributes only ~28 patches; the ~400
Leaf-derived performance patches in Keila's stack must be re-ported onto the
26.1.2 base by hand, and Keila takes over maintaining them instead of inheriting
Leaf's upstream work.

## Key structural insight

Keila does **not** dynamically depend on Leaf. The root `build.gradle.kts` forks
Paper directly (`paperweight { upstreams.paper { ref = paperCommit … } }`) and the
Leaf patch stack is *vendored* under `leaf-server/` and `leaf-api/`. So this
re-base is mostly content + base-version work, not a paperweight rewire:

1. move the Paper base from `1.21.11` (`c5eb079`) to `26.1.2` (`76d2ac7`);
2. replace the vendored Leaf patch set with Purpur 26.1.2's base patches plus the
   re-ported performance patches Keila wants to keep;
3. rename/reidentify from Leaf to Purpur.

## Procedure

1. **Base + toolchain** (`gradle.properties`, build files):
   - `mcVersion`/`apiVersion = 26.1.2`, `version = 26.1.2-R0.1-SNAPSHOT`,
     `paperCommit = 76d2ac7…`, drop the decoupled-label scaffolding
     (`keilaVersion`, manifest override, README "Upstream build base" row).
   - `mache:26.1.2+build.3`; refresh the single-file `build.gradle.kts` patches
     against Paper `main` (it removed spigot mappings/reobf + reflection-rewriter
     and bumped deps — see `26.1.2-migration.md`).
   - **Java 21 -> 25** across root + subproject toolchains, `options.release`,
     CI `setup-java`, `.java-version`, README; audit `--enable-preview` usages.
   - Bump paperweight-patcher to a build compatible with the 26.1.2 toolchain
     (Purpur uses `2.0.0-beta.21`).
2. **Vendor Purpur's base patches**: copy Purpur 26.1.2's `purpur-server` /
   `purpur-api` patches in as the new base layer (rename dirs to `keila-server` /
   `keila-api`, or keep a `purpur-*` base + `keila-*` overlay split). Enumerate
   the exact 28 via the contents API / a checkout once the build env is available.
3. **Re-port the performance stack**: take the ~400 non-Purpur patches currently
   under `leaf-server/minecraft-patches` + `leaf-server/paper-patches` +
   `leaf-api/paper-patches` and reconcile each against the decompiled 26.1.2
   source. Drop any now provided by Purpur or upstreamed into Paper. Respect
   `docs/upstream/patch-risk-index.md`: P0/P1 patches need stress + soak tests and
   rollback notes per `docs/upstream/sync-policy.md`.
4. **Identity**: README + `docs/keila/identity.md` reframe Keila as a fork of
   **Purpur** (+ Paper), not Leaf; update attribution and the lineage line.
   `scripts/upstreamCommit.sh` should track Purpur `ver/26.1.2` and Paper `main`
   instead of Leaf.
5. **Build + verify** (capable env): `./gradlew applyAllPatches`, reconcile,
   `./gradlew check createMojmapPaperclipJar`, then `scripts/verifyLocal.sh`.

## Environment requirements (unchanged from the platform bump)

The re-port needs a paperweight run against decompiled 26.1.2 source. That run
needs network egress to `repo.papermc.io` (mache), `piston-meta.mojang.com`
(vanilla jar), and `maven.purpurmc.org`/GitHub for Purpur, plus a **Java 25**
JDK. In the Claude Code web session used to author this, those PaperMC/Mojang
hosts return HTTP 403 and the JDK is 21, so the re-port cannot run here — it must
run on a network-capable, Java 25 environment (e.g. the project's CI runners,
which already reach these hosts).
